**架构错乱隐患（重点）**：

1. **双写入源**：ZCode 的 projection 是"核心权威、UI 只读、snapshot 整体替换"；jasmine 里 ViewModel 既在 `collectEvents` 里实时写会话状态，又保留"keep-warm 冷掉后从核心读转写重建"的恢复路径（ChatViewModel.kt:1441 注释："acquire 命中接着渲染，冷掉才回落核心读转写"）。订阅式单一写入方被塞进命令式 UDF 后，"信实时流还是信回放"靠 30 秒 keep-warm 计时器裁决——rekey、会话删除、回合失败等边界全靠手工对齐，是典型的双写竞态温床。

2. **状态机语义降级**：六态形状抄全了，但驱动源只有一半——实时路径由 ViewModel 推进（ToolCalled→RUNNING、失败→FAILED、停止→STOPPED），恢复路径只有"有没有结果"一档信息，缺省 COMPLETED；`PENDING`/`DENIED` 在 Kotlin 侧是自承的死值（ChatViewModel.kt:146 "留给还没做的审批流程"）。"状态是数据不从结果反推"这条总原则在恢复路径上被自己的默认值打破。

3. **类型驱动 UI 挂在字符串数据上**：渲染分流架子是 enum/类型驱动的（ToolCallKind），数据源却是参数文本 + 结果文本的正则式抠取（`patchTextOf`/`todoItemsOf`/`unescape`）。ZCode 每类 renderer 消费的是结构化 payload；这里工具产出形状一变就静默降级到 PLAIN 或空块，没有 zod schema 那种运行时校验兜底。

4. **FFI 边界丢了协议校验**：TS 侧 `rows.ts` 用 zod `conversationRowSchema` 做运行时校验；Rust↔Kotlin 边界上 `tool_status` 是裸字符串、`reasoningEffort` 用空串表"未设置"、`AgentOutputLanguage` 与 `agent_settings.rs` 靠注释约定"同值，改要一起改"。协议一致性从"schema 保证"退化为"注释纪律"。

5. **生命周期语义缺口**：ZCode 的 stop 是订阅通道一等命令；jasmine 的 Rust 轮次是阻塞调用，MODULE_MAP §2.1 记载"取消 Flow 不会中断核心的轮次"。Kotlin 侧的 `isInterruptRequested`/`STOPPED` 是 UI 层补出来的状态，与核心真实轮次生命周期存在时间窗错位（已请求中断但核心仍在吐事件）。

6. **规模错配导致同步不可持续**：ZCode 把职责分散在 store / projection / 50+ renderer / hooks 各层；jasmine 把投影、事件归约、渲染分流、动画参数全压进 ChatViewModel.kt（117KB）+ ChatScreen.kt（101KB）两个文件，文件内散布 30+ 处"照 ZCode 第 X 行"的人工对照点。上游 ZCode 一升级，没有结构性同步机制，只能逐点人工比对——CHAT 文档 §六记录的"并发编辑同一文件互相覆盖写坏文件"已是这一隐患的现实症状。

## 5. 设计问题
1. **错误处理丢失**: AgentFailure 单变体 Failed{detail}（ffi/lib.rs:224-228）——所有错误塌缩成字符串；Kotlin 侧 ChatEvent.Failed(detail) 也是字符串。HTTP 状态码、可重试性、错误类别全丢；界面想区分"网络错误 vs 配额"只能字符串匹配。AgentError 在 Rust 侧有类型（service.rs:68-87），边界上被 detail() 抹平（ffi/lib.rs:291-293 等每一处 map_err）。
2. **每调用一个 tokio runtime**: block_on 每次新建 current_thread runtime（service.rs:1552-1557）。一轮对话期间 runtime 活着没问题，但 (a) 建/销 runtime 开销每轮一次；(b) 跨轮没有共享的连接池？不对——reqwest client 在 Attached 里（start_conversation 时建，service.rs:254-262），连接池是 client 级，跨 runtime 没问题（reqwest 的连接池不绑 runtime…实际上 reqwest 的 hyper 连接池绑 runtime 句柄？hyper 0.14+ 的 pool 需要 runtime 来 spawn 连接任务；在不同 current_thread runtime 上 block_on 复用同一 reqwest::Client 是可以的，因为请求在该 runtime 上驱动）。这个不深究，但值得提"runtime 生命周期 vs client 生命周期错位"的风险。
3. **同步阻塞 JNI + 取消语义**: send 是阻塞调用，整个 turn 期间占住一个 Dispatchers.IO 线程。取消链路：Flow 取消 → handle.interrupt → CancellationToken → drain_stream 的 select 跳出 → TurnAborted → Aborted 事件。但：(a) 中断只在 await 点被看到，HTTP 请求中途/工具执行中的批次会跑完（turn.rs:130-132 注释明说一批工具必须跑完）；(b) Kotlin 侧 events channel 是 UNLIMITED（RustAgentChat.kt:169），核心推事件不背压，UI 卡顿时内存增长；(c) 工具执行没有取消（parallel.rs 的 JoinSet 不响应 cancellation token）。
4. **事件模型不一致**: Rust 侧 ChatEvent 有 Usage 事件"不是回合结束"（RustAgentChat.kt:283-284 endsTurn 特判），Completed 从 thread.on_response_event 里被过滤掉、由 run_turn 末尾统一发（turn.rs:186-189, 147）——同一事件在两个地方产生/抑制，时序依赖隐性约定。UserPromptRequested 作为"回合终止事件"（endsTurn()=true），但 Rust 侧它并不是终态——turn 只是 break 了（turn.rs:117-119），Kotlin 侧把它当 flow 结束。语义对齐靠 Kotlin 端约定维持。
5. **会话状态两侧各存一份**: Rust 侧 Attached{history, thread, rollout}（内存）+ rollout JSONL（磁盘）；Kotlin 侧 RustConversationStore 自己缓存 MutableStateFlow<List<Conversation>>，且**它是另一个 AgentHandle 实例**（RustConversationStore.kt:28）——与 RustAgentChat 的 handle 是两个 AgentChatService，各自有独立 sessions map。附着状态不共享：store 的 handle 永不附着（注释里明说），靠文件当真源。风险：send 进行中转写已追加，但 conversationsStateFlow 要等有人调 refresh() 才更新（push vs poll）；删除会话时 delete_conversation 只删自己 service 的槽（service.rs:871-876 先 end_conversation），如果另一条 RustAgentChat 实例正附着同一会话并跑着 turn，那个实例的 Attached 不会被清——文件被删后它的下一轮 record_boundary 会写失败。
6. **AgentHandle 生命周期**: UniFFI Object 靠 GC + 析构释放；RustAgentChat 没有显式 close()，进程内多个 RustAgentChat（非 Singleton DI）各持一个 AgentChatService 与 ToolRegistry/工具，直到 GC。正在跑的 turn 持有 slot Arc，service 被 drop 后 turn 仍能完成（内存安全），但 rollout 文件句柄等资源的释放时机不确定。
7. **文档滞后**: MODULE_MAP.md（2026-09-27）说"停止/中断一轮尚未实现"（§1.1 第 59 行）、"⚠️ 待接"（§2.1 停止回复），但代码里 interrupt/recover_turn/Aborted 已完整实现（service.rs:809、RustAgentChat.kt:73-78、DEEPSEEK 文档 2026-09-28 已含 interrupt 验证）。§2.2 里 "Chat Completions 报文 ⚠️ 待接" 也已实现。

## 5. Rust↔Kotlin 边界上的设计问题

1. **错误信息在边界被系统性抹平**。Rust 侧 `AgentError` 有类型（service.rs:68-87 区分 NoSession/Transport/Poisoned/Transcript），边界统一 `AgentFailure::Failed{detail}`（ffi/lib.rs:224-228），到 Kotlin 再塌缩成 `ChatEvent.Failed(String)`。界面想区分"网络错/配额错/配置错"只能字符串匹配中文/英文报错文本。且 `probe` 走另一套（返回 `ProbeResult` 而非 `Result`），两种错误风格并存。更隐蔽的是 `conversations()`/`transcript()` 在核心内部就把 IO 错误吞成空 Vec（service.rs:879-893、897-902）——"目录坏了"与"没有会话"对平台不可区分。
2. **每调用新建一个 tokio runtime**（service.rs:1552-1557）。turn 级操作（send/respond/recover）每次现建现销 current_thread runtime；reqwest client 却活在 `Attached` 里跨轮复用（service.rs:254-262 建造、365 行入槽），连接池与 runtime 生命周期错位。功能上可行，但每次 turn 白付 runtime 建销成本，也让"全局一个 runtime"式的资源治理（统一计时器、指标）无从谈起。
3. **取消是协作式、且粒度粗**。Flow 取消→`handle.interrupt`→`CancellationToken`→只在 `drain_stream` 的 select 点被看到（turn.rs:160-164）；一批工具调用必须整批跑完才响应中断（turn.rs:130-132 注释明说，为避免留下无结果的 tool_call），`ToolCallRuntime` 的 `JoinSet` 本身不响应取消（parallel.rs:108 只是 join_next）。HTTP 非流式段、工具执行段都不可中断；用户感知上的"停止"最多延迟到当前采样流结束 + 整批工具落定。
4. **事件模型靠隐性约定对齐**。`ChatEvent.Usage` 不是回合终止（RustAgentChat.kt:283-284 特判），`Completed` 在 thread 映射层被 `continue` 吞掉、由 `run_turn` 末尾统一发（turn.rs:186-189、147）——同一事件一处产生一处抑制；`UserPromptRequested` 在 Kotlin 侧是 flow 终止事件（`endsTurn()=true`），在 Rust 侧只是 turn 循环 `break`（turn.rs:117-119）外加 `thread.is_paused_for_prompt()` 状态，两侧靠"发问后核心不再发事件"这条约定维持一致。任一改动都不会有编译错误，只有时序 bug。
5. **会话状态多实例并存 + 两侧各存一份**。Kotlin 侧 `RustConversationStore` 与每个 `RustAgentChat` 各持一个 `AgentHandle`（各是一个 `AgentChatService`，各有独立 sessions map）。附着状态互不可见：`delete_conversation` 只清自己 service 的槽再删文件（service.rs:871-876）——若另一个 `RustAgentChat` 实例正附着同一会话跑 turn，文件被删后它的下一次落盘会失败。`conversationsStateFlow` 是 poll 模型：核心写文件不会推给 Kotlin，必须有人记得调 `refresh()`，跑 turn 期间列表就是陈旧的。对话内容也双份：Rust 内存 `Attached.history` + rollout JSONL 是真源，Kotlin UI 层的消息列表又是一份镜像。
6. **无背压**。`Channel.UNLIMITED`（RustAgentChat.kt:169）+ 核心在 JNA 线程上同步推事件：UI 繁忙时事件在堆里无限排队（作者注释里是有意取舍——宁可占内存不可丢 token，但与"流式节流"目标相悖，长回复 + 卡 UI 时是内存隐患）。
7. **生命周期靠 GC**。`AgentHandle` 无显式 `close()`；非单例 DI 下进程里可同时存在 N+1 个 `AgentChatService`（各带 ToolRegistry/工具/槽表），直到 GC 触发 UniFFI 析构。正在跑的 turn 持有 `Arc<SessionSlot>` 内存上安全，但 rollout 文件句柄等资源释放时机不确定。
8. **文档滞后于代码**。MODULE_MAP.md（标 2026-09-27）仍写"停止/中断一轮尚未实现（Rust 侧是阻塞调用，取消 Flow 不会中断核心的轮次）"（L59）、"停止回复 ⚠️ 待接"（L75）、"Chat Completions 报文 ⚠️ 待接"（L84-85）——实际 `interrupt`/`recover_turn`/`Aborted` 与 Chat wire 均已实现并在真机验证（DEEPSEEK_CHAT_TOOL_CALLS.md §6，2026-09-28）。以该文档为对照依据时会得到过时的缺口清单。
9. **小不一致**：`send` 的 Kotlin 接口注释承诺"only cancellation propagates"，但 `coreEvents` 的 worker 只捕 `AgentFailure`（RustAgentChat.kt:182-184）——核心侧 panic（如 `Poisoned` 之外的 mutex 中毒路径、UniFFI 自身校验错）会以未捕获异常穿出 `Dispatchers.IO` worker，Flow 直接异常终止而非 `ChatEvent.Failed`。

## 二、Rust 核心分析（对照 codex-rs）

移植纪律总体不错，[MODULE_MAP.md](file:///D:/ima/minimal-hello/rust/MODULE_MAP.md) 逐项登记了裁剪面（MCP、沙箱、审批、exec、compact、realtime、多 agent 全删），DeepSeek 双 wire 协议适配有真机实测文档（[DEEPSEEK_CHAT_TOOL_CALLS.md](file:///D:/ima/minimal-hello/rust/DEEPSEEK_CHAT_TOOL_CALLS.md)）。关键事实：

- **桥接方式**：UniFFI 0.32.2 proc-macro + JNA（非手写 JNI）。注解直接长在 `jasmine-protocol` / `jasmine-model-provider-info` 的真类型上，FFI 侧 `AgentHandle` 暴露约 20 个方法，事件回推走 `EventListener` 回调（非 channel/polling）
- **线程模型**：核心全 async、边界全同步——**每次调用现场新建一个 current_thread tokio runtime**（`block_on`），在 Kotlin `Dispatchers.IO` 线程上跑完整个 turn，事件在同一线程同步回调进 Kotlin
- **取消**：`interrupt()` → `CancellationToken` → turn 在下一个 await 点收手；**一批工具调用必须整批跑完才响应中断**
- Kotlin 侧 [core/agent](file:///D:/ima/minimal-hello/core/agent/src/main/java/com/lhzkml/jasmine/core/agent/AgentChat.kt)：`RustAgentChat` 把回调包成 `Flow<ChatEvent>`（`Channel.UNLIMITED`，作者有意取舍：宁可占内存不丢 token），Flow 取消 = 中断该会话

**Rust 侧结构性问题**（按影响排序）：

1. **错误在边界被系统性抹平**：Rust 的 `AgentError`（NoSession/Transport/Poisoned/Transcript 四型）→ UniFFI 单变体 `AgentFailure.Failed{detail}` → Kotlin `ChatEvent.Failed(String)`。UI 想区分"网络错/配额错/配置错"只能匹配报错文本
2. **会话真源多实例并存**：`RustConversationStore` 与每个 `RustAgentChat`（**故意非单例**）各持一个 `AgentHandle` → 各是一个 `AgentChatService`，附着状态互不可见；一个实例删会话文件时，另一个实例可能正附着它跑 turn
3. **会话列表是 poll 模型**：核心写文件不会推给 Kotlin，必须有人记得调 `refresh()`——跑 turn 期间列表是陈旧的，全靠 `endTurn` 里手动发 `ChatEffect.RefreshConversations` 补救
4. **每调用新建 tokio runtime**，但 reqwest client 跨轮复用——连接池与 runtime 生命周期错位
5. **`AgentHandle` 无显式 close，生命周期靠 GC** 触发 UniFFI 析构
6. 文档滞后：MODULE_MAP.md 仍写"中断尚未实现"，实际已实现并真机验证；`Cargo.toml` 照抄 codex workspace deps 带一堆死重（ratatui/v8/aws-*/landlock/sentry/keyring + 3 条 github git 依赖）
